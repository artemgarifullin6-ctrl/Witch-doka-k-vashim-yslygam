== 2. Практическая реализация и этапы рефакторинга

=== 2.1. Шаг №1. Прямое битовое управление через регистры GPIO
Начальный этап разработки включал построение линейного алгоритма циклического переключения светодиодных индикаторов («бегущие огни»). Программа оперирует адресами периферии `GPIOA` и `GPIOC` непосредственно в теле главной функции `main()`.

.Исходный код первой программы (Процедурный подход)
[source,cpp]
----
#include "rccregisters.hpp" // for RCC
#include "gpioaregisters.hpp" // for GPIOA
#include "gpiocregisters.hpp" // for GPIOC

std::uint32_t SystemCoreClock = 16'000'000U;

extern "C" {
    int __low_level_init(void)
    {
        RCC::CR::HSION::On::Set();
        while (RCC::CR::HSIRDY::NotReady::IsSet())
        {
        }
        RCC::CFGR::SW::Hsi::Set();
        while (!RCC::CFGR::SWS::Hsi::IsSet())
        {
        }
        RCC::APB2ENR::SYSCFGEN::Enable::Set();
        return 1;
    }
}

void delay(int cycles)
{
    for (int i = 0; i < cycles; ++i)
    {
        asm volatile("");
    }
}

int main()
{
    RCC::AHB1ENR::GPIOAEN::Enable::Set();
    RCC::AHB1ENR::GPIOCEN::Enable::Set();

    GPIOA::MODER::MODER5::Output::Set();
    GPIOC::MODER::MODER5::Output::Set();
    GPIOC::MODER::MODER8::Output::Set();
    GPIOC::MODER::MODER9::Output::Set();

    for (;;)
    {
        GPIOC::ODR::ODR5::High::Set();
        delay(1000000);
        GPIOC::ODR::ODR8::High::Set();
        delay(1000000);
        GPIOC::ODR::ODR9::High::Set();
        delay(1000000);
        GPIOA::ODR::ODR5::High::Set();
        delay(1000000);

        GPIOC::ODR::ODR5::Low::Set();
        delay(1000000);
        GPIOC::ODR::ODR8::Low::Set();
        delay(1000000);
        GPIOC::ODR::ODR9::Low::Set();
        delay(1000000);
        GPIOA::ODR::ODR5::Low::Set();
        delay(1000000);
    }
    return 1;
}
----

=== 2.2. Шаг №2. Наращивание функционала и усложнение процедурной модели
Для наглядного выявления системных недостатков монолитного кода в программу были внедрены дополнительные итерационные циклы. Светодиоды переводятся в режим работы с чередованием фаз активности (прогон одиночной волны с последующим сдвигом парных сигналов).

Расширение логики привело к перегрузке функции `main()` рутинными операциями и снижению прозрачности кода. Любое гипотетическое изменение аппаратной схемы (смена маски пинов или перенос линий на другой порт) привело бы к необходимости полной переработки алгоритмической составляющей.

=== 2.3. Шаг №3. Объектно-ориентированная декомпозиция и полиморфный диспетчер
С целью устранения сильной связанности модулей была спроектирована новая объектная модель на основе разделения проекта на абстрактные контракты и реализации. Исходные коды распределены по двум директориям рабочей области IAR Workspace: `Contracts` (интерфейсы `ILed`, `IMode`) и `Implementation` (`Pin`, `Led`, классы прикладных режимов).

В рамках данного шага в систему были интегрированы разработанные компоненты, включая шаблонную абстракцию пинов и объектную обертку индикаторов. На основе созданной базы был написан финальный вариант программы, реализующий инвариантный диспетчер режимов.

.Исходный код третьей программы (Объектно-ориентированный подход)
[source,cpp]
----
#include <array>
#include "rccregisters.hpp" // for RCC
#include "gpioaregisters.hpp" // for GPIOA
#include "gpiocregisters.hpp" // for GPIOC
#include "Pin.h" // for Pin
#include "Led.h" // for Led
#include "ModeBlink.h" // for ModeBlink
#include "ModeTree.h" // for ModeTree
#include "ModeChess.h" // for ModeChess

std::uint32_t SystemCoreClock = 16000000U;
extern "C" int __low_level_init(void)
{
  RCC::CR::HSION::On::Set();
  while (RCC::CR::HSIRDY::NotReady::IsSet())
  {
  }
  
  RCC::CFGR::SW::Hsi::Set();
  while (!RCC::CFGR::SWS::Hsi::IsSet())
  {
  }
  
  RCC::APB2ENR::SYSCFGEN::Enable::Set();
  return 1;
}

void delay(int cycles)
{
  for (int i = 0; i < cycles; ++i)
  {
    asm volatile ("");
  }
}

Pin<GPIOC::ODR,5> pin5;
Pin<GPIOC::ODR,8> pin8;
Pin<GPIOC::ODR,9> pin9;
Pin<GPIOA::ODR,5> pin5a;
Led led1(pin5a);
Led led2(pin9);
Led led3(pin8);
constexpr std::uint32_t ledsCount = 3U;
std::array<ILed*, ledsCount> leds = {&led1,&led2,&led3};
ModeBlink <ledsCount> modeBlink(leds);
ModeTree <ledsCount> modeTree(leds);
ModeChess <ledsCount> modeChess(leds);
constexpr std::uint32_t modesCount = 3U;
std::array<IMode*, modesCount> modes = {&modeBlink, &modeTree, &modeChess};
constexpr std::uint32_t DELAYS_PER_10S = 100U;

int main(void)
{
  RCC::AHB1ENR::GPIOAEN::Enable::Set();
  RCC::AHB1ENR::GPIOCEN::Enable::Set();
  
  GPIOA::MODER::MODER5::Output::Set();
  GPIOC::MODER::MODER5::Output::Set();
  GPIOC::MODER::MODER8::Output::Set();
  GPIOC::MODER::MODER9::Output::Set();
  std::uint32_t modeNumber = 0;

  while (1)
  {
    for (std::uint32_t i = 0; i < DELAYS_PER_10S / ledsCount; ++i){
      modes[modeNumber] -> Work();
      delay(1000000);
    }
    modeNumber = (modeNumber + 1) % modesCount;
    modes[modeNumber] -> Init();
  }
}
----

== 3. Проектирование компонентной архитектуры периферии

=== 3.1. Шаблонный класс Pin (Implementation/Pin.h)
Обобщенный класс `Pin` осуществляет конкретизацию методов абстракции `IPin`. Благодаря механизму метапрограммирования (`template`), конфигурация порта (`TPort`) и позиция вывода (`pinNum`) передаются как аргументы сборки. Это позволяет компилятору разворачивать битовые сдвиги `1U << pinNum` непосредственно в коде во время сборки. В итоге генерируется максимально легковесный машинный код без создания тяжеловесных таблиц виртуальных методов времени выполнения (концепция Zero-cost abstractions).

[source,cpp]
----
#ifndef UNTITLED2_IMPLEMENTATION_PIN_H
#define UNTITLED2_IMPLEMENTATION_PIN_H

#include <cassert>
#include "IPin.h"

template <typename TPort, int pinNum>
class Pin final : public IPin
{
  public:
    void Set() override
    {
      TPort::Set(uint8_t(1U) << pinNum);
    }

    void Reset() override
    {
      //TPort::Reset(uint8_t(1U) << pinNum);
    }

    void Toggle() override
    {
      TPort::Toggle(uint8_t(1U) << pinNum);
    }

    bool GetState() const override
    {
      assert(true);
    }
};

#endif
----

=== 3.2. Интерфейс ILed (Contracts/ILed.h)
Задает единый программный контракт для управления абстрактной световой индикацией. Прикладные модули верхнего уровня взаимодействуют только с методами смены состояний `Light()`, `PutOut()` и `Toggle()`, сохраняя полную независимость от топологии платы.

[source,cpp]
----
#ifndef UNTITLED2_CONTRACTS_ILED_H
#define UNTITLED2_CONTRACTS_ILED_H

class ILed
{
public:
    virtual void Light() = 0;
    virtual void PutOut() = 0;
    virtual void Toggle() = 0;

    virtual ~ILed() = default;
};

#endif //UNTITLED2_CONTRACTS_ILED_H
----

=== 3.3. Класс Led (Implementation/Led.h)
Финальный класс `Led` реализует функционал индикатора через паттерн внеднения зависимостей, используя ссылку на интерфейсный объект `IPin&`. Конструктор связывает конкретный экземпляр светодиода с абстрактным аппаратным выводом. Данный подход гарантирует высокую гибкость: переназначение линий ввода-вывода происходит без изменения внутренней логики работы светодиодного компонента.

[source,cpp]
----
#ifndef UNTITLED2_IMPLEMENTATION_LED_H
#define UNTITLED2_IMPLEMENTATION_LED_H

#include "ILed.h"
#include "IPin.h"

class Led final : public ILed
{
private:
    IPin& pin;

public:
    explicit Led(IPin& pin)
        : pin(pin)
    {
    }

    void Light() override
    {
        pin.Set();
    }

    void PutOut() override
    {
        pin.Reset();
    }

    void Toggle() override
    {
        pin.Toggle();
    }
};

#endif //UNTITLED2_IMPLEMENTATION_LED_H
----

=== 3.4. Контейнер std::array и интерфейс IMode (Contracts/IMode.h)
Для безопасного хранения светодиодов и исключения рисков выхода за границы массивов в ООП-модели задействован статический контейнер `std::array`. Контейнер инкапсулирует размер на этапе компиляции, гарантируя Zero-overhead в ОЗУ. Применение динамического `std::vector` исключено для предотвращения фрагментации кучи.

Интерфейс `IMode` унифицирует запуск прикладных режимов, предоставляя методы инициализации `Init()` и пошагового выполнения `Work()`.

[source,cpp]
----
#ifndef UNTITLED2_CONTRACTS_IMODE_H
#define UNTITLED2_CONTRACTS_IMODE_H

class IMode
{
public:
    virtual void Init() = 0;
    virtual void Work() = 0;

    virtual ~IMode() = default;
};

#endif //UNTITLED2_CONTRACTS_IMODE_H
----

== 4. Пошаговый рефакторинг и сборка третьей программы на занятии

В ходе практической части занятия мы последовательно прошли путь декомпозиции монолитной логики, исправляя ошибки сборки и решая аппаратные проблемы отладочной платы.

=== 4.1. Конфигурирование пинов и обход аппаратной неисправности
Объявление физических пинов выполнено через шаблонный класс `Pin`. На данном этапе возникло аппаратное ограничение: у отладочной платы Владимира был зафиксирован дефект вывода `PC5`.

Для обхода неисправности мы оперативно переназначили первый светодиодный индикатор на работоспособный порт `GPIOA` (вывод `PA5`). Объект `pin5` был сохранен в кодовой базе конфигурации, но исключен из прикладного массива:

[source,cpp]
----
Pin<GPIOC::ODR,5> pin5; // Исключен из работы из-за неисправности пина платы
Pin<GPIOC::ODR,8> pin8;
Pin<GPIOC::ODR,9> pin9;
Pin<GPIOA::ODR,5> pin5a; // Исправный аппаратный пин, на который перенесен led1

Led led1(pin5a);
Led led2(pin9);
Led led3(pin8);
----

=== 4.2. Агрегирование объектов в контейнеры
Все созданные светодиоды были агрегированы нами в массив типа `std::array` под управлением базового интерфейса `ILed`. Мы жестко зафиксировали размер аппаратной группы константой `ledsCount = 3U`:

[source,cpp]
----
constexpr std::uint32_t ledsCount = 3U;
std::array<ILed*, ledsCount> leds = {&led1, &led2, &led3};
----

После этого мы инициализировали три объекта режимов. Преподаватель поставил задачу спроектировать проект с заделом масштабируемости под три сценария, включая шахматный режим `ModeChess`, логику которого было решено отладить в качестве домашнего задания. Указатели объектов были собраны в прикладной массив `modes`:

[source,cpp]
----
ModeBlink <ledsCount> modeBlink(leds);
ModeTree <ledsCount> modeTree(leds);
ModeChess <ledsCount> modeChess(leds);

constexpr std::uint32_t modesCount = 3U;
std::array<IMode*, modesCount> modes = {&modeBlink, &modeTree, &modeChess};
----

=== 4.3. Реализация безопасной программной задержки
Чтобы исключить вырезание пустого цикла оптимизатором компилятора IAR при сборке релиза, мы внедрили в функцию задержки ассемблерный барьер `asm volatile ("")`:

[source,cpp]
----
void delay(int cycles)
{
  for (int i = 0; i < cycles; ++i)
  {
    asm volatile ("");
  }
}
----

При проектировании временных интервалов был выявлен важный нюанс. Шаг цикла вычисляется как выражение `DELAYS_PER_10S / ledsCount` (100 / 3). Из-за правил целочисленного деления в C++ цикл выполняется ровно 33 раза вместо 33.333. Преподаватель указал на эту «шляпу с циклами», отметив, что она дает погрешность — режим активен чуть меньше 10 секунд. В дальнейшем данный программный костыль будет переписан на аппаратный таймер.

=== 4.4. Инвариантный главный цикл main()
Итоговый код третьей программы включает в себя высокоуровневую диспетчеризацию. Мы настроили направления работы портов в регистре `MODER` и запустили абстрактный цикл:

[source,cpp]
----
#include <array>
#include "rccregisters.hpp" // for RCC
#include "gpioaregisters.hpp" // for GPIOA
#include "gpiocregisters.hpp" // for GPIOC
#include "Pin.h" // for Pin
#include "Led.h" // for Led
#include "ModeBlink.h" // for ModeBlink
#include "ModeTree.h" // for ModeTree
#include "ModeChess.h" // for ModeChess

// Инициализация SystemCoreClock и __low_level_init (аналогично Шагу №1)

constexpr std::uint32_t DELAYS_PER_10S = 100U;

int main(void)
{
  RCC::AHB1ENR::GPIOAEN::Enable::Set();
  RCC::AHB1ENR::GPIOCEN::Enable::Set();
  
  GPIOA::MODER::MODER5::Output::Set();
  GPIOC::MODER::MODER5::Output::Set();
  GPIOC::MODER::MODER8::Output::Set();
  GPIOC::MODER::MODER9::Output::Set();
  std::uint32_t modeNumber = 0;

  while (1)
  {
    for (std::uint32_t i = 0; i < DELAYS_PER_10S / ledsCount; ++i){
      modes[modeNumber] -> Work();
      delay(1000000);
    }
    modeNumber = (modeNumber + 1) % modesCount;
    modes[modeNumber] -> Init();
  }
}
----

Переключение индексов «по кольцу» осуществляется через арифметический остаток от деления (`% modesCount`), избавляя код от громоздких ветвлений `if-else`. Метод `Init()` вызывается при каждой смене режима для принудительного сброса внутренних итераторов (например, шага в «бегущих огнях» / «ёлочке»), предотвращая запуск алгоритма из некорректного промежуточного состояния.

== 5. Запуск программы и подготовка среды выполнения до main()

Параллельно с практической сборкой программы мы изучили низкоуровневые аппаратные процессы, протекающие в микроконтроллере STM32F411 до момента входа в пользовательский `main()`.

=== 5.1. Обработка вектора сброса и распределение памяти стека
Сразу после снятия сигнала сброса (`Reset`) ядро считывает конфигурационные данные из таблицы векторов, аппаратно привязанной к адресу `0x08000000`. Первое машинное слово определяет начальную позицию указателя стека (Stack Pointer). Для функционирования стека выделяется область объемом `0x200`. Стек инкрементируется сверху вниз (в сторону убывания адресов ОЗУ) и требует строгого выравнивания по границе 8 байт.

Второе машинное слово таблицы содержит физический адрес обработчика сброса (`Reset Handler`), который аппаратно загружается компилятором в счетчик команд процессора (`PC`) для старта системных процедур инициализации среды `__iar_program_start` и `__cmain`.

=== 5.2. Подготовка сегментов ОЗУ и выполнение __low_level_init()
До вызова `main()` библиотечный стартовый код IAR выполняет критически важные операции по подготовке оперативной памяти:
* Секция непроинициализированных глобальных переменных принудительно обнуляется.
* Глобальные переменные с явной инициализацией заполняются актуальными значениями, автоматически копируемыми из Flash-памяти программ в ОЗУ.

Внутри этого процесса, строго до копирования переменных, вызывается пользовательская функция низкоуровневой конфигурации `__low_level_init()`. Возвращаемое значение `1` подтверждает успешность этапа и разрешает дальнейший запуск микроконтроллера.

В ходе проверки и развёртывания разработанного программного обеспечения на стенде были зафиксированы следующие практические результаты:

. *Сборка и прошивка процедурного кода:* Процедурные версии программ (Шаг №1 и Шаг №2) успешно скомпилированы в среде IAR. С помощью внутрисхемного программатора *ST-Link* бинарные файлы перенесены во флеш-память МК *STM32F411*. Тестирование первого варианта подтвердило циклическое переключение пинов `PC5` -> `PC8` -> `PC9` -> `PA5`. Проверка усложненного варианта подтвердила смену паттернов индикации: после 3 циклов поочередного включения стабильно воспроизводились 2 цикла парного мигания каналов (`PA5`/`PC8` и `PA5`/`PC9`). При этом на плате Владимира светодиод, подключенный к `PC5`, не функционировал, что наглядно подтвердило критическую уязвимость жесткой привязки алгоритма к физическим адресам портов.
. *Проверка ООП-модели:* Логическая структура каталогов `Contracts` и `Implementation` была успешно развернута в проекте прямо во время занятия. Компилятор без предупреждений обработал заголовочные файлы `IPin.h`, `Pin.h`, `ILed.h` и `Led.h`. Переназначение ссылки на объект `pin5a` (`GPIOA::ODR,5`) вместо неисправного `pin5` в конструкторе `Led led1(pin5a)` позволило мгновенно восстановить полную работоспособность индикации на дефектной плате без изменения единой строчки кода в алгоритмах самих режимов (`ModeBlink` и `ModeTree`).
. *Анализ оптимизации:* Проведена верификация генерации кода для параметризованного шаблона `Pin`. Путем анализа ассемблерного листинга доказано, что вычисление масок пинов `uint8_t(1U) << pinNum` происходит на этапе компиляции, а быстродействие не уступает прямой процедурной записи в регистры периферии (концепция Zero-cost abstractions).
. *Пошаговая отладка автомата переключения:* С помощью точек останова (`Breakpoints`) в IAR IDE мы верифицировали работу высокоуровневого цикла `while(1)` в функции `main()`. Проверка показала, что вызов `modes[modeNumber]->Init()` корректно сбрасывает внутренние счетчики шагов режима при переключении (например, итератор шага в «бегущих огнях» / «ёлочке»), предотвращая наложение состояний. Арифметика остатка от деления `(modeNumber + 1) % modesCount` стабильно переключает указатели по кольцу, избавляя код от громоздких ветвлений `if-else`. Из-за целочисленного деления констант времени (`100 / 3`) зафиксировано выполнение 33 итераций за квант, что дает небольшую погрешность в итоговый 10-секундный интервал. При работе с указателями для вызова метода через указатель на базовый интерфейс используется оператор `->`, а для вызова через объект напрямую — оператор `.`. Имена методов в интерфейсах и классах реализации полностью совпадают.

== 7. Результаты работы и дальнейшее развитие

В результате сформирована устойчивая ООП-архитектура управления светодиодами, в которой аппаратные выводы, светодиоды и режимы индикации представлены независимыми слабосвязанными компонентами.

Основной цикл не содержит подробной логики каждого режима. Он работает через интерфейс `IMode`, а режимы обращаются к светодиодам через интерфейс `ILed`. Это упрощает расширение проекта и позволяет изменять порядок подключения светодиодов через конфигурацию массива `leds`, не переписывая алгоритмы режимов.

В качестве следующего этапа предусмотрено дальнейшее расширение набора режимов, в том числе проверка шахматного режима `ModeChess`, а также последующее выделение управления режимами в отдельный управляющий класс (Менеджер режимов) для сокращения кода `main()`.

== 8. Выводы по работе

В ходе выполнения лабораторной работы были исследованы современные методики разделения абстракций при создании программного обеспечения для микроконтроллерных систем на C++. Мы детально изучили низкоуровневые этапы пуска ядра STM32F411, включая инициализацию стека (`0x200`) с выравниванием по границе 8 байт, а также механизмы работы системных процедур `__iar_program_start` and `__cmain` по подготовке сегментов ОЗУ до входа в пользовательский `main()`.

Наглядное сравнение монолитной структуры (с вложенными циклами и хардкодом в `main`) и объектно-ориентированной модели показало преимущество последней в задачах масштабирования и сопровождения кода. Внедрение шаблонного класса `Pin`, класса `Led` и абстрактных интерфейсов `ILed` и `IMode` совместно со статическими контейнерами `std::array` позволило полностью изолировать прикладные задачи от физического уровня периферии. Спроектированная архитектура инвариантного главного цикла гарантирует возможность добавления новых алгоритмов индикации (таких как домашний шахматный режим `ModeChess`) исключительно через расширение конфигурационного массива `modes` без необходимости какого-либо вмешательства в критически важный исполняемый код диспетчера.
